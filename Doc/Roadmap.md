# 開発ロードマップ

## 1. 概要

`Doc/Spec.md` をもとに、半自動マッピングツールの初版から運用可能な形までを段階的に実装するためのロードマップを整理する。
初版では、探索しながら地図が埋まり、必要な箇所だけ素早く修正できる体験を最優先にする。

## 2. ゴール / 非ゴール

### ゴール

- Web ブラウザで動作する Explore / Map の 2 モード UI を提供する
- セルとエッジを分離したデータ構造で、探索結果を安定して記録できるようにする
- キーボード主体で探索し、マウスで補正できる基本導線を成立させる
- 階層管理、保存、再読込まで含めて継続利用できる状態にする

### 非ゴール

- 初版から PixiJS / WebGL ベースの高機能描画基盤を導入すること
- 複雑な互換レイヤや将来拡張のためだけの抽象化を先回りで入れること
- 共有機能、オンライン同期、複数人編集を初版スコープに含めること

## 3. 前提

- フロントエンドは React + TypeScript + Vite を前提とする
- 状態管理は Zustand を採用する
- マップ描画は HTML5 Canvas 2D を採用する
- 保存形式は JSON を主軸にし、自動保存は localStorage を優先する
- オート補完の既定値は `Basic` を採用する

## 4. 開発方針

- まず「歩ける、記録される、直せる」を成立させ、その後に保存や補助機能を積む
- データモデルを先に固め、UI はその制約を見える形に整理する
- fail fast を前提にし、要件が明示されるまで互換対応やフォールバックは増やさない
- 各フェーズで「ユーザーが何を確認できるか」を明確にし、段階ごとに動作確認可能な状態を保つ

## 5. フェーズ別ロードマップ

### Phase 0: 基盤構築

目的:
開発速度を落とさない最小限の土台を先に揃える。

成果物:

- React + TypeScript + Vite のアプリ基盤
- Tailwind CSS を含む基本 UI レイアウト
- Zustand ストアの雛形
- Canvas 描画領域と左右ペインの骨格
- 型定義ファイルとディレクトリ構成の初期整理

完了条件:

- アプリが起動し、固定サイズのグリッドと基本 UI が表示できる
- 型定義と状態更新の責務が分離されている

### Phase 1: マップ中核モデル

目的:
セル、エッジ、プレイヤー状態を破綻なく保持できる土台を作る。

成果物:

- `cells`, `vEdges`, `hEdges`, `icons` のデータモデル
- プレイヤー位置と向きの状態管理
- Canvas へのグリッド、床、壁、プレイヤー描画
- 座標系と表示範囲の基礎ロジック

完了条件:

- 任意のセルやエッジ状態をストアに保持できる
- 状態変更が Canvas に即時反映される

### Phase 2: Explore モード

目的:
探索しながら地図が埋まるコア体験を最短で成立させる。

成果物:

- `W/A/S/D` または矢印による移動
- 移動時の `floor` / `open` 自動記録
- `Off` / `Basic` / `Corridor` のオート補完設定
- 探索モード時に「移動した事実を優先」する更新ルール
- 現在地、向き、モードの明示表示

完了条件:

- プレイヤー移動に応じて床と通路が自動記録される
- `Basic` を既定値として破綻しにくい探索フローが成立している

### Phase 3: Map モードと手動編集

目的:
探索結果を人手で素早く補正できる編集体験を入れる。

成果物:

- Explore / Map のモード切替
- Map モード時の既知壁衝突判定
- 前方エッジに対するショートカット編集
- セルクリック、境界クリックによるマウス編集
- アイコンパレットと足元 / 前方セルへの配置

完了条件:

- キーボード主体の登録とマウス補正が両立する
- マップ整合性の確認用として Map モードが機能する

### Phase 4: 階層・保存・再開

目的:
単発の試作ではなく、継続利用できる道具にする。

成果物:

- 階層一覧と切替 UI
- 階層の追加、削除、複製
- JSON 保存 / 読込
- localStorage 自動保存
- ビューポート状態の保存

完了条件:

- 複数階層を独立して編集できる
- 保存したデータを再読込して作業を再開できる

### Phase 5: 操作性の強化

目的:
日常利用でのストレスを減らし、修正コストを下げる。

成果物:

- Undo / Redo
- ズーム / パン
- 右 / 下方向のグリッド拡張
- 選択中ツールやアイコンの状態表示
- 空、読込失敗、保存成功などの UI 状態整備

完了条件:

- 誤操作から復帰できる
- 途中でグリッド不足になっても作業継続できる

### Phase 6: 仕上げ

目的:
初版公開や継続改善の起点にできる品質まで整える。

成果物:

- PNG 出力
- 階段リンクなどの補助機能
- キーボードショートカット一覧
- 基本的な利用ガイド
- 主要操作の回帰確認手順

完了条件:

- 初回利用者が主要機能を迷わず試せる
- 継続開発時に壊れやすい導線が把握できている

## 6. 優先順位

1. Phase 0 から Phase 3 までを MVP とする
2. Phase 4 を「継続利用可能版」の必須条件とする
3. Phase 5 以降は利用負荷と改善効果を見て順次投入する

## 7. 横断タスク

- 型定義と状態更新ルールの文書化
- キー操作とモード差分の UI 表示
- データ破損を防ぐための保存フォーマット version 管理
- 主要ユースケースの手動確認手順整備

## 8. リスクと対策

- データモデルが曖昧なまま UI 実装を進めると、後半で差し戻しが増える
  対策: Phase 1 の時点で `cells` / `edges` / `icons` の責務を固定する
- Explore と Map のルール差分が曖昧だと、操作ミスが増える
  対策: モード表示と操作制約を常時 UI に出す
- 保存仕様の後付けで互換性コストが増える
  対策: Phase 4 までに JSON schema 相当の構造を固め、`version` を持たせる

## 9. Definition of Done

- Explore モードで移動しながら地図が埋まる
- Map モードで既知の壁を越えずに整合性確認できる
- 壁、ドア、アイコンをキーボードまたはマウスで編集できる
- 複数階層を保持し、JSON 保存 / 読込で再開できる
- 基本操作を第三者が追える程度のドキュメントが揃っている
